# Taylor Shift — Ticket Shop infrastructure

Infrastructure and configuration for the Taylor Shift PrestaShop ticket shop:
**Terraform** provisions the AWS resources, **Ansible** configures the instances and
deploys the shop from the generic `prestashop/prestashop` image.

```
                         ┌──────────────── internet ────────────────┐
                              │ HTTP(S)                │ SSH (your IP only)
                    ┌─────────▼──────────┐   ┌─────────▼─────────┐
   public subnets   │ Application LB     │   │ Bastion (Ansible) │   AZ a + AZ b
                    └─────────┬──────────┘   └─────────┬─────────┘
                              │ HTTP 80                │ SSH 22
                    ┌─────────▼────────────────────────▼─────────┐
   private app      │  EC2 × N — Docker — prestashop/prestashop  │   one per AZ
   subnets          └───┬─────────────────────────────────────┬──┘
                        │ MySQL 3306                          │ NFS 2049
                    ┌───▼──────────────────┐        ┌─────────▼──────────────┐
   private data     │ RDS MySQL 8.0        │        │ EFS — document root,   │
   subnets          │ (Multi-AZ in prod)   │        │ media, PHP sessions    │
                    └──────────────────────┘        └────────────────────────┘

   Secrets Manager → DB password (read by the instance role, never by a human)
   CloudWatch      → unhealthy hosts / latency / 5xx alarms
```

Everything the instances need to know — database endpoint, EFS id, load balancer
name — travels from Terraform to Ansible through the **Terraform state**: the
inventory is generated by `cloud.terraform.terraform_provider`, so no address is
ever copied by hand.

## 1. Prerequisites

| Tool | Version | Notes |
|---|---|---|
| Terraform | ≥ 1.6 | 1.10+ uses S3 native state locking |
| Ansible | ≥ 2.15 (`ansible-core`) | plus `ansible-galaxy`, `ansible-vault` |
| AWS CLI | v2 | credentials with rights to create VPC/EC2/RDS/EFS/ALB/IAM |
| SSH client | any | used through the bastion |

```sh
aws sts get-caller-identity     # must succeed before anything else
```

## 2. Create the Terraform state backend (once per AWS account)

The state contains generated secrets, so it lives in a versioned, encrypted S3
bucket with locking. `bootstrap/` creates it and writes `terraform/backend.tf`
for you:

```sh
./scripts/bootstrap-backend.sh dev      # dev | staging | prod
```

It prints the generated `backend.tf` (bucket, key `<env>/terraform.tfstate`,
locking). `terraform/backend.tf` is git-ignored because the bucket name is
account specific — `terraform/backend.tf.example` shows what it looks like.
Without this step Terraform falls back to a local state file, which works for a
solo test but not for a team.

## 3. Deploy

```sh
terraform -chdir=terraform init
terraform -chdir=terraform apply                      # dev, ~12 min (RDS is the slow part)

ansible-galaxy install -r ansible/requirements.yml    # collections + the docker role
ansible-inventory -i ansible/inventory.yml --graph    # hosts read from the Terraform state
ansible-playbook  -i ansible/inventory.yml ansible/site.yml --ask-vault-pass
```

Run every command **from the repository root** (`ansible.cfg` and the inventory
paths are relative to it). Vault password for this demo repository:
`taylorshift`.

The first playbook run installs the shop (a one-shot container runs the
PrestaShop installer against the empty database, then disappears); it takes a
few minutes. A second run reports **no change** — the container that serves the
shop is always created with the installer disabled.

Then:

```sh
terraform -chdir=terraform output shop_url      # front office
terraform -chdir=terraform output admin_url     # back office
```

Back-office credentials are in `ansible/group_vars/all/vault.yml`
(`ansible-vault view ansible/group_vars/all/vault.yml`).

### Other environments

```sh
./scripts/bootstrap-backend.sh prod
terraform -chdir=terraform init -reconfigure
terraform -chdir=terraform apply -var-file=environments/prod.tfvars
```

| | dev | staging | prod |
|---|---|---|---|
| App instances | 1 × t3.small | 2 × t3.small | 3 × t3.medium |
| AZs / NAT gateways | 2 / 1 | 2 / 1 | 3 / 3 |
| Database | db.t3.micro, single-AZ | db.t3.small, single-AZ | db.t3.medium, **Multi-AZ** |
| Backups | 1 day | 3 days | 14 days + EFS backup |
| Deletion protection | off | off | on (DB + ALB) |

Sizing lives in `terraform/locals.tf` (`env_defaults`); anything can still be
overridden per environment in `terraform/environments/*.tfvars`.

## 4. How requests reach the shop, and what happens when traffic grows

**Path of a request.** DNS → Application Load Balancer (one node per public
subnet, i.e. per AZ) → round-robin over the healthy EC2 targets → PrestaShop
container → RDS for the catalogue and orders, EFS for pictures, themes and PHP
sessions.

**Handling a ticket-sales rush.** The application tier is stateless: no order,
picture or session is stored on an instance. Scaling out is therefore a number:

```sh
terraform -chdir=terraform apply -var app_instance_count=6
ansible-playbook -i ansible/inventory.yml ansible/site.yml --ask-vault-pass
```

Terraform creates the instances, spreads them over the AZs and registers them in
the target group; the inventory picks them up automatically and the playbook
configures **only** what is not converged yet. Existing instances keep serving
throughout. The database follows with a bigger `db_instance_class` (vertical) and
RDS storage autoscaling; EFS throughput is `elastic` in production, so it follows
the load on its own.

When to scale is not guesswork: the CloudWatch alarms created with the ALB watch
`TargetResponseTime` (> 2 s over 3 minutes = the fleet is saturated),
`UnHealthyHostCount` and `HTTPCode_Target_5XX_Count`, and notify the SNS topic
(`alarm_email`).

**If an instance becomes unavailable.** The target group polls `/health.php`
every 15 s; after 2 failures (≈ 30 s) the instance is taken out of rotation and
in-flight requests are drained for 30 s. Customers keep browsing on the
remaining instances, and keep their cart and their session because sessions live
on EFS, not on the instance. Recovery is `terraform apply -replace=...` followed
by the playbook. If a whole AZ fails, the ALB stops using its node, the
instances of the other AZs absorb the traffic and — in production — RDS fails
over to its standby in 60–120 s.

**Limits of this design, honestly.**

- Scaling is **declarative, not automatic**: a sudden spike needs an operator to
  run two commands (~3 min). The next step is to bake the Ansible result into an
  AMI (Packer) and put an Auto Scaling group behind the same target group; the
  role and the health endpoint are already written for it.
- The whole document root sits on **EFS**, which makes every instance
  interchangeable but adds NFS latency on PHP includes. It is the right trade-off
  at this size; past a few thousand requests per minute, ship the code inside the
  image and keep only `img/` on EFS, with a CDN in front.
- **One writable database.** Reads can be offloaded to an RDS read replica, but
  PrestaShop writes to a single primary.
- The stack is **single-region**. A regional outage means downtime.
- The **bastion** is the single SSH entry point: if it is down, Ansible cannot
  reach the fleet (the shop itself is unaffected, and the instances also accept
  SSM Session Manager).

## 5. Design choices

| Component | Where it runs | Why |
|---|---|---|
| PrestaShop | Docker on **EC2** | The subject requires an Ansible-configured EC2 instance; a container keeps the runtime identical everywhere and makes a version change a one-line variable. |
| Database | **RDS MySQL** (managed) | Backups, patching, Multi-AZ failover and monitoring are the parts nobody wants to hand-roll during a ticket rush. Running MySQL on EC2 would mean owning all of it. |
| Shared files | **EFS** | Several instances must serve the same pictures and sessions. S3 would need a PrestaShop module; EBS cannot be shared. |
| Entry point | **ALB** | Health checks, connection draining, sticky cookies and free horizontal scaling across AZs. |
| Secrets | **Secrets Manager** + **Ansible Vault** | The database password is generated by Terraform, never leaves AWS, and is read by each instance with its own IAM role. Only the shop's back-office credentials are in the repository, encrypted. |
| SSH | **Bastion** | Application instances have no public IP. One audited entry point, locked to the operator's IP. |

Other decisions worth knowing:

- **Instances have no public address**; outbound traffic goes through NAT
  gateways (one per AZ in production), and S3 traffic through a free gateway
  endpoint.
- **IMDSv2 is mandatory** on every instance, so an SSRF in the shop cannot steal
  the instance role.
- `/health.php` is **shallow on purpose**: it does not touch MySQL, because a
  database hiccup marking all instances unhealthy at once would turn a degraded
  shop into an unreachable one.
- The shop URL stored in the database is **reconciled on every run** with the
  current load balancer name, which is what makes the stack redeployable from
  scratch.

## 6. Day-to-day operations

```sh
# Ship a configuration change (idempotent, safe to re-run)
ansible-playbook -i ansible/inventory.yml ansible/site.yml --ask-vault-pass

# Only the application layer
ansible-playbook -i ansible/inventory.yml ansible/site.yml --ask-vault-pass --tags prestashop

# One instance
ansible-playbook -i ansible/inventory.yml ansible/site.yml --ask-vault-pass --limit taylorshift-dev-app-2

# Upgrade PrestaShop: change prestashop_image in ansible/group_vars/prestashop/main.yml
# (take an RDS snapshot first), then run the playbook.

# Shop logs
ssh -i $(terraform -chdir=terraform output -raw ssh_private_key_path) ubuntu@$(terraform -chdir=terraform output -raw bastion_public_ip)
ssh ubuntu@<app private ip> 'sudo docker logs --tail 100 prestashop'

# Read the database credentials (they are nowhere in Git)
aws secretsmanager get-secret-value --secret-id $(terraform -chdir=terraform output -raw database_secret_name)

# Change a vault secret
ansible-vault edit ansible/group_vars/all/vault.yml

# Tear an environment down (the state backend is kept)
./scripts/destroy.sh dev
```

**Replacing a sick instance**

```sh
terraform -chdir=terraform apply -replace='module.compute.aws_instance.app[1]'
ansible-playbook -i ansible/inventory.yml ansible/site.yml --ask-vault-pass
```

## 7. Repository layout

```
bootstrap/              S3 + DynamoDB backend for the Terraform state (run once)
scripts/                bootstrap-backend.sh, destroy.sh
terraform/
  main.tf               composition of the six modules
  locals.tf             per-environment sizing (dev / staging / prod)
  ansible.tf            inventory published into the state (ansible provider)
  environments/         one tfvars per environment
  modules/network       VPC, 3 subnet tiers, NAT, routes, S3 endpoint, flow logs
  modules/security      security groups, written as one rule per resource
  modules/storage       EFS + one mount target per AZ
  modules/database      RDS MySQL, parameter group, Secrets Manager
  modules/compute       app instances, bastion, IAM instance profile
  modules/loadbalancer  ALB, target group, listeners, CloudWatch alarms
ansible/
  inventory.yml         cloud.terraform.terraform_provider (dynamic)
  requirements.yml      Galaxy collections + geerlingguy.docker
  site.yml              bastion play + application play
  group_vars/           all/ (+ encrypted vault.yml), prestashop/, bastion/
  roles/common          packages, timezone, hostname, journald, motd
  roles/efs             NFS client and the shared mount
  roles/prestashop      credentials, PHP config, one-shot install, container
```

## 8. Troubleshooting

| Symptom | Cause and fix |
|---|---|
| `ansible-inventory --graph` shows no host | `terraform apply` has not run, or you are not in the repository root. |
| `502/503` from the load balancer | Targets not healthy yet; check `/health.php` on the instance and `sudo docker logs prestashop`. |
| Playbook cannot reach the instances | Your public IP changed: `terraform apply` again (the bastion rule follows it) or set `admin_ssh_cidrs`. |
| `Attempting to decrypt but no vault secrets found` | Add `--ask-vault-pass`. |
| Installer times out | Read the container log the failure prints; usually the database security group or a wrong secret. |
